🗒️ Spring Boot로 만든 Notion 스타일 메모 앱 — 백엔드 흐름 완전 분해

서버가 켜지는 순간부터 응답이 클라이언트에게 돌아갈 때까지, 그 사이에 무슨 일이 일어나는지 한 줄씩 따라가봅니다.

📌 어떤 앱이냐면…

Notion처럼 페이지를 계층 구조로 정리하고 회의록 템플릿으로 시작할 수 있는 1인용 메모 웹앱. 스택은 Spring Boot 3 + JPA + MySQL (백엔드), React (프론트). 이 글은 백엔드에 집중합니다.

🗂️ 백엔드 폴더 구조

13단계나 돼 보이지만 우리가 직접 짠 코드는 ④⑤⑥⑨⑩ 다섯 군데뿐입니다. 나머지는 Spring이 해줘요.

🚀 ① 서버가 처음 켜질 때 무슨 일이?

📄 파일: MeetingNotesApplication.java

@SpringBootApplication
public class MeetingNotesApplication {
    public static void main(String[] args) {
        SpringApplication.run(MeetingNotesApplication.class, args);
    }
}

이 단 5줄짜리 파일이 사실 엄청난 일을 합니다. SpringApplication.run() 안에서 일어나는 일을 순서대로 풀면:

1) 컴포넌트 스캔 — "이 폴더에 누가 있는지 다 찾아와"

@SpringBootApplication이 붙은 클래스의 패키지와 그 하위 폴더 전부를 뒤져서 @Component, @Service, @Repository, @RestController 같은 어노테이션이 붙은 클래스들을 모조리 찾아냅니다.

우리 프로젝트에선 이런 것들이 발견돼요:

  • @RestController: PageController, AuthController, TagController
  • @Service: PageService, AuthService, TagService
  • @Repository(자동 구현): PageRepository, TagRepository, UserRepository
  • @Component: JwtAuthenticationFilter, JwtUtil
  • @Configuration: SecurityConfig, CorsConfig, JpaAuditingConfig

2) 빈(Bean) 생성과 의존성 주입

찾아낸 클래스들을 객체로 만들어서 보관함(ApplicationContext)에 넣어둡니다. 이렇게 보관된 객체를 "빈(Bean)"이라고 불러요. 콩알처럼 한 알 한 알 만들어 저장한다는 느낌.

이때 PageService가 PageRepository를 필요로 하면, Spring이 알아서 꺼내서 넣어줍니다. 이게 그 유명한 의존성 주입(DI)이에요.

@Service
@RequiredArgsConstructor    // ← Lombok이 생성자를 자동 생성
public class PageService {
    private final PageRepository pageRepository;   // ← Spring이 알아서 넣어줌
    private final UserRepository userRepository;
    private final TagRepository tagRepository;
    // ...
}
💡 왜 final로 받냐? 생성자에서 한 번 주입받고 평생 안 바뀌도록. @RequiredArgsConstructor는 final 필드만 받는 생성자를 자동 생성하는 Lombok 어노테이션이에요.

3) DataSource 연결 — DB 커넥션 풀 준비

application.yml에 적힌 DB 주소·계정을 읽어서 커넥션 풀(HikariCP)을 만듭니다. 매 요청마다 DB 접속 새로 만들면 너무 느리니까, 미리 커넥션을 10개쯤 만들어놓고 빌려쓰는 구조.

4) JPA가 엔티티 → 테이블 매핑

@Entity 붙은 클래스(Page, User, Tag)를 보고 DB 테이블 구조를 검증/생성합니다. 설정(spring.jpa.hibernate.ddl-auto)에 따라 자동 생성/검증만 함.

5) Security 필터 체인 조립

📄 파일: config/SecurityConfig.java

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())                                    // ① CSRF 끔 (JWT 쓰니까)
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))       // ② 세션 안 씀
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()                  // ③ 로그인 API는 누구나
            .anyRequest().authenticated()                                  // ④ 나머지는 로그인 필요
        )
        .addFilterBefore(jwtAuthFilter,                                   // ⑤ 우리 필터 끼워넣기
                         UsernamePasswordAuthenticationFilter.class)
        .build();
}

각 줄이 하는 일:

  • ① CSRF 끔: CSRF 공격 방어는 쿠키 세션 기반일 때 필요. JWT는 헤더에 직접 담아 보내니까 불필요.
  • ② STATELESS: 서버가 세션을 안 들고 있음. 누구인지는 매 요청의 토큰으로만 판단.
  • ③ permitAll: 로그인/회원가입 URL은 토큰 없어도 통과 (없으면 로그인 자체를 못 함).
  • ④ authenticated: 나머지 모든 URL은 인증된 사용자만.
  • ⑤ addFilterBefore: 우리 JWT 필터를 표준 인증 필터 앞에 끼워넣음. 토큰을 먼저 검사해서 SecurityContext에 사용자를 넣어야 하니까.

6) Tomcat 시작 → 8080 포트 listen

여기까지 끝나면 콘솔에 "Started MeetingNotesApplication" 메시지가 뜨고 요청을 기다립니다.

🛬 ② 요청이 도착하면 — 필터 체인의 여정

예시 요청: GET /api/pages/42, 헤더에 Authorization: Bearer eyJ...

단계 ②-1: JwtAuthenticationFilter — 토큰 검문소

📄 파일: auth/JwtAuthenticationFilter.java

protected void doFilterInternal(HttpServletRequest request,
                                HttpServletResponse response,
                                FilterChain chain) {

    // ⓐ 헤더에서 "Bearer xxx" 형태 추출 → xxx 부분만 꺼냄
    String token = resolveToken(request);

    // ⓑ 토큰이 있고 유효하면 (서명·만료 확인)
    if (token != null && jwtUtil.isValid(token)) {

        // ⓒ 토큰 페이로드에서 이메일 추출
        String email = jwtUtil.extractEmail(token);

        // ⓓ DB에서 사용자 정보 조회
        UserDetails userDetails = userDetailsService.loadUserByUsername(email);

        // ⓔ "이 요청은 이 사람이 보낸 거다"라는 인증 객체 생성
        UsernamePasswordAuthenticationToken auth =
            new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());

        // ⓕ SecurityContext에 저장 → 컨트롤러에서 @AuthenticationPrincipal로 받을 수 있게 됨
        SecurityContextHolder.getContext().setAuthentication(auth);
    }

    // ⓖ 다음 필터로 (토큰 없거나 잘못돼도 그냥 통과 — 인증 안 된 상태로 다음 단계 진입)
    chain.doFilter(request, response);
}

중요한 디테일 세 가지:

  • 토큰이 없어도 여기서 막지 않습니다. 그냥 인증 안 된 상태로 통과. 막는 건 그 다음 단계(authorizeHttpRequests)가 함.
  • SecurityContext는 ThreadLocal에 저장됩니다. 같은 요청을 처리하는 동안만 유지되고 응답 나가면 비워져요.
  • OncePerRequestFilter를 상속해서 한 요청에 한 번만 실행되도록 보장.

단계 ②-2: 인가 체크 — "들어갈 자격 있어?"

필터 체인 끝에서 Spring Security가 SecurityConfig의 규칙을 보고 판단합니다. "/api/pages/**는 authenticated만 가능" 인데 SecurityContext에 인증 정보가 있으면 통과, 없으면 401 Unauthorized로 즉시 반환.

💡 검문소 vs 입장 심사:
JwtAuthenticationFilter = "이 신분증 진짜야?" (인증, Authentication)
authorizeHttpRequests = "이 신분증으로 이 방에 들어갈 수 있어?" (인가, Authorization)

🚦 ③ DispatcherServlet — 스프링의 중앙 관제탑

필터를 통과한 요청은 DispatcherServlet이라는 단일 진입점으로 옵니다. 스프링이 알아서 만들어주는 거라 우리가 코드를 짤 일은 없지만, 여기서 컨트롤러를 찾아 호출하는 핵심 단계예요.

  1. HandlerMapping이 "GET /api/pages/42는 어느 메서드로 가야 하나?"를 결정합니다. 우리가 컨트롤러에 붙인 @GetMapping("/{id}")를 보고 매칭.
  2. HandlerAdapter가 그 메서드의 파라미터를 채워서 호출합니다:
    • @PathVariable Long id → URL의 "42"를 Long으로 변환해서 넣음
    • @RequestBody PageRequest req → HTTP 본문 JSON을 PageRequest 객체로 변환 (Jackson)
    • @AuthenticationPrincipal UserDetails user → SecurityContext에서 사용자 꺼냄
  3. 준비된 파라미터로 컨트롤러 메서드 호출.

📄 파일: page/PageController.java

@RestController
@RequestMapping("/api/pages")
public class PageController {

    private final PageService pageService;

    @GetMapping("/{id}")
    public ResponseEntity<ApiResponse<PageResponse>> get(
            @PathVariable Long id,                          // ← URL의 {id}
            @AuthenticationPrincipal UserDetails user) {    // ← 토큰에서 추출된 사용자

        // 컨트롤러는 얇게! 서비스에 위임만.
        return ResponseEntity.ok(
            ApiResponse.ok(pageService.get(id, user.getUsername()))
        );
    }
}
💡 컨트롤러는 왜 얇아야 하나? 컨트롤러는 "HTTP 계층"이에요. 비즈니스 로직이 여기 들어가면 나중에 같은 로직을 다른 곳(예: 스케줄러, 메시지 큐 핸들러)에서 재사용할 때 컨트롤러를 거쳐야 하는 이상한 구조가 됩니다.

🎫 ④ Service 호출 — @Transactional의 비밀

📄 파일: page/PageService.java

@Service
@RequiredArgsConstructor
@Transactional                                  // ← 핵심! 클래스 모든 메서드에 적용
public class PageService {

    private final PageRepository pageRepository;
    private final UserRepository userRepository;

    @Transactional(readOnly = true)             // ← 메서드별로 덮어쓸 수도 있음
    public PageResponse get(Long id, String email) {
        Page page = getPageOwned(id, email);    // ① 권한 검증 + 조회
        return PageResponse.from(page);         // ② 엔티티 → DTO 변환
    }

    private Page getPageOwned(Long id, String email) {
        Page page = pageRepository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("페이지를 찾을 수 없습니다."));
        if (!page.getUser().getEmail().equals(email)) {
            throw new IllegalArgumentException("접근 권한이 없습니다.");
        }
        return page;
    }
}

@Transactional이 진짜로 하는 일

"트랜잭션을 시작한다"는 게 마법 같은 한 줄로 끝날 리가 없죠. 실제로 일어나는 일은 프록시(proxy) 패턴입니다. 

// 우리가 호출하는 PageService는 사실 진짜 PageService가 아니라
// Spring이 만든 "가짜 PageService(프록시)"입니다.

class PageService$$ProxyByCGLIB extends PageService {     // ← Spring이 런타임에 생성

    public PageResponse get(Long id, String email) {
        // ① 트랜잭션 시작 (DB 커넥션 받기 + setAutoCommit(false))
        TransactionStatus tx = txManager.getTransaction();
        try {
            // ② 진짜 메서드 호출
            PageResponse result = super.get(id, email);
            // ③ 정상 종료면 커밋
            txManager.commit(tx);
            return result;
        } catch (RuntimeException e) {
            // ④ 예외 터지면 롤백
            txManager.rollback(tx);
            throw e;
        }
    }
}

그러니까 우리가 짠 pageService.get(...) 한 줄은 실제로:

  1. 프록시가 가로채서 트랜잭션 시작
  2. 실제 PageService의 get() 실행
  3. 리턴되면 커밋, 예외면 롤백
🐛 프록시 함정: 같은 클래스 안에서 메서드를 호출하면 프록시를 안 거칩니다.
예: public void a() { this.b(); } 에서 b()에 @Transactional 붙여도 a()를 외부에서 부르면 b()의 트랜잭션은 적용 안 됨. 직접 호출이라 프록시를 패싱하기 때문.

readOnly = true의 이점

@Transactional(readOnly = true)를 붙이면 JPA가 변경 감지(Dirty Checking)를 건너뛰어서 성능이 좋아집니다. 조회 전용 메서드엔 꼭 붙여요.

권한 검증을 Service에서 하는 이유

"URL이 인증된 사용자만 통과한다"는 것과 "그 사용자가 이 데이터에 접근해도 되느냐"는 다른 문제입니다.

  • 로그인은 했지만 → 다른 사람의 페이지 id로 GET 요청 → 막아야 함
  • 그래서 Service의 모든 메서드에서 getPageOwned로 소유자 검증
// 더 까다로운 케이스 — 페이지 이동 시 새 부모도 검증
public PageResponse move(Long id, Long newParentId, String email) {
    Page page = getPageOwned(id, email);              // ① 옮길 페이지 소유자 검증
    Page newParent = newParentId != null
        ? pageRepository.findById(newParentId).orElseThrow(...) : null;
    if (newParent != null && !newParent.getUser().getEmail().equals(email)) {
        throw new IllegalArgumentException("접근 권한이 없습니다.");   // ② 새 부모 소유자 검증
    }
    // ③ 순환 참조 방지 — newParent의 조상 사슬에 자기 자신이 있나?
    Page cursor = newParent;
    while (cursor != null) {
        if (id.equals(cursor.getId())) {
            throw new IllegalArgumentException("순환 참조: 후손을 부모로 설정할 수 없습니다.");
        }
        cursor = cursor.getParent();
    }
    page.setParent(newParent);                        // ④ 부모만 바꾸면 끝 — UPDATE는 자동
    return PageResponse.from(page);
}

주목: setParent 한 번 부르고 끝입니다. UPDATE pages SET parent_id = ? WHERE id = ?는 누가 날렸을까요? 다음 섹션에서 설명합니다.

💾 ⑤ Repository — JPA가 SQL을 만드는 비밀

📄 파일: page/PageRepository.java

public interface PageRepository extends JpaRepository<Page, Long> {

    // ① 메서드 이름만 잘 지으면 → JPA가 SQL 자동 생성
    List<Page> findByUserIdAndParentIsNullOrderBySortOrderAsc(Long userId);

    // ② 복잡하면 JPQL 직접 작성
    @Query("SELECT p FROM Page p WHERE p.user.id = :userId " +
           "AND (p.title LIKE %:q% OR p.content LIKE %:q%)")
    List<Page> searchByKeyword(@Param("userId") Long userId, @Param("q") String q);

    // ③ N+1 회피용 — JOIN FETCH로 부모까지 한 번에 가져오기
    @Query("SELECT p FROM Page p LEFT JOIN FETCH p.parent " +
           "WHERE p.user.id = :userId ORDER BY p.sortOrder ASC")
    List<Page> findAllByUserIdForTree(@Param("userId") Long userId);
}

메서드 이름이 SQL이 되는 마법

JPA는 findBy로 시작하는 메서드 이름을 파싱해서 SQL을 만들어냅니다:

메서드 이름 생성되는 SQL (대략)
findById(42L) SELECT * FROM pages WHERE id = 42
findByUserId(1L) SELECT * FROM pages WHERE user_id = 1
findByUserIdAndParentIsNull(1L) SELECT * FROM pages WHERE user_id = 1 AND parent_id IS NULL
...OrderBySortOrderAsc() ... ORDER BY sort_order ASC
findByFavoriteTrue(...) ... WHERE favorite = true

영속성 컨텍스트 — JPA의 1차 캐시

@Transactional 안에서 조회한 엔티티는 영속성 컨텍스트(EntityManager)라는 메모리 공간에 저장됩니다. 트랜잭션이 끝날 때까지 거기 살아있어요. 

@Transactional
public void someMethod() {
    Page page = pageRepository.findById(42L).get();   // SQL 한 번 나감, 영속성 컨텍스트에 저장
    Page same = pageRepository.findById(42L).get();   // SQL 안 나감! 컨텍스트에서 가져옴

    System.out.println(page == same);                  // true — 완전히 같은 객체
}

Dirty Checking — UPDATE가 자동으로 나가는 이유

아까 page.setParent(newParent)만 부르고 UPDATE 쿼리를 안 날렸는데도 DB가 바뀌었죠? 그건 Dirty Checking 때문입니다.

  1. JPA가 처음 엔티티를 조회할 때 "스냅샷"을 같이 저장해둠
  2. 트랜잭션 끝나기 전(=커밋 직전)에 영속성 컨텍스트에 있는 모든 엔티티를 스냅샷과 비교
  3. 변경된 필드가 있으면 자동으로 UPDATE 쿼리 생성·실행
@Transactional
public PageResponse update(Long id, PageRequest req, String email) {
    Page page = getPageOwned(id, email);     // ① 조회 → 영속 상태 + 스냅샷 저장
    page.update(req.title(), req.content(), req.emoji());   // ② 필드만 변경
    return PageResponse.from(page);          // ③ return — 메서드 종료
    // ④ 프록시가 commit() 직전 dirty check → UPDATE 쿼리 자동 실행
}
📌 정리: JPA의 핵심 가치는 "객체 필드를 바꾸기만 하면 DB도 알아서 바뀐다"는 것. 개발자는 SQL을 거의 안 쓰고도 비즈니스 로직에 집중할 수 있어요.

📦 ⑥ 응답 직렬화 — 객체가 JSON이 되는 순간

Service가 반환한 PageResponse는 자바 객체입니다. 클라이언트는 JSON을 받죠. 그 사이를 채우는 게 Jackson이에요.

📄 DTO 파일: page/dto/PageResponse.java

// Java 14+의 record — 불변 데이터 클래스를 한 줄로
public record PageResponse(
    Long id,
    String title,
    String content,
    String emoji,
    boolean favorite,
    List<TagResponse> tags,
    LocalDateTime updatedAt
) {
    public static PageResponse from(Page page) {
        return new PageResponse(
            page.getId(), page.getTitle(), page.getContent(),
            page.getEmoji(), page.isFavorite(),
            page.getTags().stream().map(TagResponse::from).toList(),
            page.getUpdatedAt()
        );
    }
}

왜 엔티티(Page) 그대로 안 보내고 DTO를 따로 만드냐:

  • 보안: Page에는 user 필드(비밀번호 해시 포함)가 들어있음 → 그대로 직렬화하면 노출!
  • 순환 참조: Page → User → 그 User의 모든 Page → … 무한 루프 직렬화로 메모리 폭발
  • API 안정성: DB 스키마가 바뀌어도 API 응답 모양은 유지 가능

📄 공통 응답 래퍼: common/ApiResponse.java

// 모든 응답을 같은 모양으로 통일
public record ApiResponse<T>(boolean success, T data, String message) {
    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>(true, data, null);
    }
    public static <T> ApiResponse<T> fail(String message) {
        return new ApiResponse<>(false, null, message);
    }
}

그래서 클라이언트가 받는 JSON은 늘 이런 모양이에요:

{
  "success": true,
  "data": {
    "id": 42,
    "title": "주간 회의",
    "content": "<p>안건 1...</p>",
    "emoji": "📋",
    "favorite": false,
    "tags": [{"id": 1, "name": "회의"}],
    "updatedAt": "2026-05-21T14:30:00"
  },
  "message": null
}

🚨 ⑦ 예외가 터지면 어디로 가나?

Service에서 throw new IllegalArgumentException("접근 권한이 없습니다.")를 던지면 어떻게 될까요? 트랜잭션은 롤백되고, 예외는 위로 위로 올라가서 DispatcherServlet까지 도달합니다. 그러면 Spring이 @RestControllerAdvice를 찾아요.

📄 파일: common/GlobalExceptionHandler.java

@RestControllerAdvice                              // ← 모든 컨트롤러에서 발생한 예외를 가로챔
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ApiResponse<Void>> handleIllegalArgument(IllegalArgumentException e) {
        return ResponseEntity.badRequest().body(ApiResponse.fail(e.getMessage()));
    }

    @ExceptionHandler(IllegalStateException.class)
    public ResponseEntity<ApiResponse<Void>> handleIllegalState(IllegalStateException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(ApiResponse.fail(e.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Void>> handleValidation(MethodArgumentNotValidException e) {
        // @Valid 검증 실패 시 첫 번째 에러 메시지만 추출
        String message = e.getBindingResult().getAllErrors().stream()
            .findFirst().map(err -> err.getDefaultMessage())
            .orElse("Validation failed");
        return ResponseEntity.badRequest().body(ApiResponse.fail(message));
    }

    @ExceptionHandler(Exception.class)                 // ← 위에서 못 잡은 모든 예외
    public ResponseEntity<ApiResponse<Void>> handleGeneral(Exception e) {
        log.error("Unhandled exception", e);
        return ResponseEntity.internalServerError().body(ApiResponse.fail("서버 오류가 발생했습니다."));
    }
}

예외 처리 흐름 전체:

① Service에서 throw new IllegalArgumentException("...");
        ▼
② @Transactional 프록시 catch → 롤백 → 다시 throw
        ▼
③ Controller가 catch 안 함 → DispatcherServlet으로 올라감
        ▼
④ DispatcherServlet이 GlobalExceptionHandler에서 매칭되는 @ExceptionHandler 찾음
        ▼
⑤ handleIllegalArgument 호출 → ResponseEntity 반환
        ▼
⑥ Jackson이 ApiResponse → JSON 변환
        ▼
⑦ HTTP 400 응답 → 클라이언트에 { "success": false, "message": "..." } 도착
💡 왜 클래스 단위로 핸들러를 모았나? 만약 모든 컨트롤러마다 try-catch를 박으면 같은 코드가 30번 반복됩니다. @RestControllerAdvice는 "전역 try-catch"를 한 곳에 모은 것.

🗄️ ⑧ 잠깐 — DB에서는 무슨 일이?

JPA가 만든 SQL이 MySQL에 도착하면 그 안에서도 일이 일어납니다. 우리가 직접 만질 일은 거의 없지만 알아두면 좋아요.

  1. 커넥션 풀에서 커넥션 빌리기 — 위에서 만들어둔 HikariCP에서 빈 커넥션 하나 받음
  2. PreparedStatement 실행 — SQL 안의 ? 자리에 파라미터 바인딩 (SQL Injection 방지)
  3. 인덱스 사용 여부 결정 — WHERE id = 42는 PK 인덱스 사용, LIKE %키워드%는 풀스캔
  4. 결과 행 반환 — JDBC ResultSet으로
  5. JPA가 ResultSet → Page 엔티티 객체로 매핑 (컬럼 ↔ 필드 매핑은 @Column 정보 사용)
  6. 커넥션 반납 — 풀로 돌려놓음

악명 높은 N+1 쿼리, 다시 짚어봄

JPA의 편리함이 함정이 되는 대표 케이스입니다.

// 처음 짠 코드 (나쁨)
public List<PageTreeResponse> getTree(String email) {
    User user = getUser(email);
    return pageRepository.findByUserIdAndParentIsNullOrderBySortOrderAsc(user.getId())
        .stream()
        .map(PageTreeResponse::from)   // ← 여기서 children을 lazy load → N+1 발생!
        .toList();
}

실제로 나가는 쿼리:

SELECT * FROM pages WHERE user_id = 1 AND parent_id IS NULL;       -- 루트 5개
SELECT * FROM pages WHERE parent_id = 1;  -- 루트1의 자식
SELECT * FROM pages WHERE parent_id = 2;  -- 루트2의 자식
SELECT * FROM pages WHERE parent_id = 3;  -- 루트3의 자식
SELECT * FROM pages WHERE parent_id = 4;
SELECT * FROM pages WHERE parent_id = 5;
SELECT * FROM pages WHERE parent_id = 11; -- 손자… 무한 증식
...

해결: 사용자 페이지를 통째로 한 번에 가져오고 메모리에서 트리 구성.

@Transactional(readOnly = true)
public List<PageTreeResponse> getTree(String email) {
    User user = getUser(email);
    List<Page> all = pageRepository.findAllByUserIdForTree(user.getId());   // 쿼리 1번

    // parentId → children 리스트 맵 만들기
    Map<Long, List<Page>> byParentId = new HashMap<>();
    List<Page> roots = new ArrayList<>();
    for (Page p : all) {
        Long pid = p.getParent() != null ? p.getParent().getId() : null;
        if (pid == null) roots.add(p);
        else byParentId.computeIfAbsent(pid, k -> new ArrayList<>()).add(p);
    }

    return roots.stream().map(p -> buildTree(p, byParentId)).toList();
}

private PageTreeResponse buildTree(Page p, Map<Long, List<Page>> byParentId) {
    List<Page> kids = byParentId.getOrDefault(p.getId(), List.of());
    List<PageTreeResponse> childResponses = kids.stream()
        .map(c -> buildTree(c, byParentId)).toList();
    return new PageTreeResponse(p.getId(), p.getTitle(), p.getEmoji(),
                                p.isFavorite(), childResponses);
}

🛫 ⑨ 응답이 돌아가는 길

여기까지 오면 응답은 거의 다 됐어요. 마지막 단계만 짧게 짚으면:

  1. Service가 PageResponse 객체 반환
  2. Controller가 ResponseEntity.ok(ApiResponse.ok(...))로 감쌈
  3. DispatcherServlet이 ResponseEntity에서 본문 객체 추출
  4. HttpMessageConverter가 객체를 → JSON으로 변환 (이때 Jackson 호출)
  5. HTTP 응답 본문에 JSON 작성 + Content-Type: application/json 헤더 추가
  6. Tomcat이 클라이언트에게 응답 전송
  7. 응답 나가는 길에 다시 필터들을 역순으로 통과
  8. SecurityContext 비워짐 (ThreadLocal 클린업)

🎯 정리: 백엔드 흐름을 한 줄로 외워봐요

🚀 부팅

SpringApplication.run → 컴포넌트 스캔 → 빈 생성 → DB 커넥션 풀 → 보안 필터 체인 조립 → Tomcat 시작

🛬 요청 처리

Tomcat → 필터(JWT 검증) → DispatcherServlet → HandlerMapping(컨트롤러 찾기) → Controller → Service(@Transactional 프록시) → Repository(JPA) → MySQL → Jackson 직렬화 → HTTP 응답

🎫 알아둘 개념

  • 의존성 주입(DI): Spring이 객체를 만들고 필요한 곳에 알아서 꽂아줌
  • 프록시 패턴: @Transactional이 동작하는 원리. 같은 클래스 내부 호출 주의!
  • 영속성 컨텍스트: 트랜잭션 안에서 엔티티가 사는 메모리 공간
  • Dirty Checking: 엔티티 필드만 바꿔도 자동 UPDATE
  • 인증(Authentication) vs 인가(Authorization): 누구냐 vs 들어갈 수 있냐
  • N+1 쿼리: 관계 lazy load의 부작용. fetch join 또는 메모리 빌드로 해결

레이어드 아키텍처를 외우는 비유

매번 헷갈리던 게 결국 한 줄 비유로 정리됐어요:

계층 역할 비유
Filter 요청 통과 전 검문 경비실 보안검색
Controller HTTP 받기·응답 만들기 민원실 접수창구
Service 로직·검증·트랜잭션 담당 직원
Repository DB 입출력 서류 창고
Entity DB 행의 자바 표현 서류 양식
DTO 외부에 노출할 형태 민원인에게 줄 결과지
ExceptionHandler 예외 → 응답 변환 민원 거절 통보 양식

이 구조를 머릿속에 박아두면 어떤 Spring Boot 프로젝트를 봐도 "이 코드가 흐름 어디에 있는지" 바로 위치를 잡을 수 있어요. 스스로 짤 때도 "이건 Controller에 들어가야 하나, Service에 들어가야 하나?" 같은 고민을 줄여줍니다.
