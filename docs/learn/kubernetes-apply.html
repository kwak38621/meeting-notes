🚀 Spring Boot + React 프로젝트를 쿠버네티스에 올리는 길 — 단계별 가이드

Notion 스타일 메모 앱(Spring Boot + React + MySQL)을 K8s로 옮기는 전 과정. 한 번에 다 옮기지 말고 점진적으로.

📸 지금 vs 옮긴 후 — 한눈에 비교

🧱 지금 (docker-compose) ☸️ 옮긴 후 (Kubernetes)
- 내 노트북에서만 돌아감
- MySQL만 컨테이너, backend/frontend는 직접 실행
- 죽으면 내가 다시 띄움
- 서버 한 대
- 새 버전 = 직접 빌드 후 재시작 		- 클러스터에서 자동으로
- backend / frontend 컨테이너화
- 죽으면 알아서 살아남
- 여러 서버에 분산 가능
- 새 버전 = 이미지 푸시 → 무중단 배포

🐳 Phase 1 — Dockerfile 작성

backend/Dockerfile

Gradle 빌드 단계와 실행 단계를 분리해서(multi-stage build — Docker 이미지를 여러 단계로 쪼개서 만드는 기법. 빌드용 이미지에서 결과물만 뽑아 가벼운 실행 이미지에 옮기는 방식) 최종 이미지 크기를 줄여요.

# 1단계: 빌드 (Gradle 캐시 활용)
FROM gradle:8.5-jdk17 AS builder
WORKDIR /app
COPY build.gradle settings.gradle ./
COPY src ./src
RUN gradle bootJar --no-daemon

# 2단계: 실행 (가벼운 JRE만)
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=builder /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app/app.jar"]

📝 용어: Gradle = 자바 빌드 도구 (Maven 같은 거). JRE = Java Runtime Environment, 자바 실행만 가능한 최소 런타임 (JDK보다 가벼움).

frontend/Dockerfile

Vite로 빌드한 정적 파일을 nginx(가볍고 빠른 웹서버. 정적 파일 서빙 / 리버스 프록시로 많이 씀)로 서빙.

# 1단계: 빌드
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# 2단계: nginx로 서빙
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx","-g","daemon off;"]

📝 npm ci = package-lock.json 기준 정확히 설치. npm install보다 빠르고 엄격해서 CI/CD에서 권장.

frontend/nginx.conf

React Router 때문에 SPA fallback(SPA는 라우팅을 브라우저가 함. 사용자가 /pages/42 같은 URL로 직접 접속하면 서버엔 그 파일이 없어 404 발생 → 어떤 URL이든 index.html을 돌려주고 React가 알아서 처리하게 함) 필요.

server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;   # SPA fallback
  }
}

🗄️ Phase 3 — MySQL은 어떻게? (가장 중요한 결정)

🤔 잠깐 — 정말 K8s에 올려야 하나?
DB를 K8s에 올리는 건 까다롭고, 실무에서도 흔히 분리합니다. 학습/소규모 프로젝트에선 안 올리는 게 더 현명할 수 있어요.
옵션 방법 난이도
A. DB는 분리 ⭐ MySQL은 docker-compose나 별도 VM에 두고, K8s엔 backend/frontend만 쉬움
B. 매니지드 DB AWS RDS, GCP Cloud SQL → 주소만 K8s에서 호출 중간
C. K8s에 올림 StatefulSet + PVC + 백업 직접 어려움

왜 분리가 정석인가

  • DB는 데이터가 영구 보존돼야 함 → K8s의 "죽으면 살리면 됨" 철학과 안 맞음
  • 백업, 복구, 버전 업그레이드를 직접 해야 함
  • StatefulSet은 일반 Deployment보다 훨씬 까다로움
  • 큰 회사들도 RDS 같은 매니지드 서비스에 맡기지 직접 운영 안 함
💡 이 글에서 진행할 방향: Option A를 따릅니다. MySQL은 docker-compose에 그대로 두고, backend가 호스트의 MySQL을 바라보게 설정. K8s에 익숙해진 후 나중에 분리 고민.

☕ Phase 4 — Backend (Spring Boot)

① ConfigMap — 설정값

# k8s/10-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "host.docker.internal"         # 호스트의 MySQL (Option A)
  DB_USER: "appuser"
  CORS_ORIGIN: "http://localhost"

② Secret — 비밀번호 🚨 매우 중요

⚠️ Secret YAML을 절대 git/깃허브에 그대로 올리지 마세요.
base64는 인코딩일 뿐 암호화가 아님. 누구나 echo "..." | base64 -d 한 줄로 디코딩 가능.

안전한 보관 방법 4가지

방법 설명
1. .gitignore + example ⭐ 실제 secret은 git 제외, secret.yaml.example 템플릿만 커밋
2. kubectl 명령으로 직접 ⭐ yaml 파일 자체를 안 만듦. 명령 한 줄로 클러스터에 주입
3. Sealed Secrets 암호화된 형태로 git에 올려도 안전. 클러스터만 복호화
4. External Secrets + Vault 비밀은 외부 보관, K8s는 참조만. 실무 표준

방법 1: .gitignore + example 패턴

.gitignore에 추가:

# 실제 secret은 절대 커밋 안 함, 템플릿은 허용
k8s/*-secret.yaml
!k8s/*-secret.yaml.example

k8s/11-secret.yaml.example (이것만 git에 커밋):

apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DB_PASSWORD: "<여기에-실제값-넣기>"
  JWT_SECRET: "<openssl rand -base64 48 결과>"

방법 2: kubectl 명령으로 직접 (더 깔끔)

kubectl create secret generic app-secret \
  --from-literal=DB_PASSWORD='실제비밀번호' \
  --from-literal=JWT_SECRET="$(openssl rand -base64 48)"

장점: git에 올릴 파일이 아예 없음.

③ Backend Deployment

# k8s/30-backend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 2                              # ← 시작은 2개로
  selector:
    matchLabels: { app: backend }
  template:
    metadata:
      labels: { app: backend }
    spec:
      containers:
        - name: backend
          image: meeting-notes-backend:1.0
          ports:
            - containerPort: 8080
          envFrom:                          # ConfigMap/Secret 모든 키를 환경변수로
            - configMapRef: { name: app-config }
            - secretRef:    { name: app-secret }
          # readinessProbe: "트래픽 받을 준비 됐어?" - 안 되면 Service가 트래픽 안 보냄
          readinessProbe:
            httpGet: { path: /actuator/health, port: 8080 }
            initialDelaySeconds: 20
          # livenessProbe: "살아있어?" - 죽었으면 컨테이너 재시작
          livenessProbe:
            httpGet: { path: /actuator/health, port: 8080 }
            initialDelaySeconds: 60

📝 Actuator = Spring Boot의 모니터링 모듈. /actuator/health로 헬스체크 가능. spring-boot-starter-actuator 의존성 추가하면 켜짐.

④ Backend Service

# k8s/31-backend-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: backend
  ports:
    - port: 8080
      targetPort: 8080
  type: ClusterIP                          # 내부 전용 (Ingress에서 호출)

🚪 Phase 6 — Ingress (외부에서 한 도메인으로)

💡 Docker Desktop K8s에서 Ingress 쓰려면 ingress-nginx controller(Ingress 규칙을 실제로 실행하는 nginx)를 먼저 설치해야 해요: 
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml
# k8s/50-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: meeting-notes-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: meeting-notes.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: backend,  port: { number: 8080 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: frontend, port: { number: 80 } }
📝 로컬에서 도메인 쓰려면 Windows의 C:\Windows\System32\drivers\etc\hosts에 한 줄 추가:
127.0.0.1 meeting-notes.local

🚦 실제 배포 — 명령어 순서

  1. 이미지 빌드
    docker build -t meeting-notes-backend:1.0 ./backend
    docker build -t meeting-notes-frontend:1.0 ./frontend
  2. Secret 만들기 (방법 2 사용 시)
    kubectl create secret generic app-secret --from-literal=...
  3. 설계도 한꺼번에 적용
    kubectl apply -f k8s/
  4. 상태 확인
    kubectl get pods — 모두 Running 인지
    kubectl get svc — 서비스 떴는지
    kubectl get ingress — Ingress IP 확인
  5. 접속 테스트 → 브라우저에서 http://meeting-notes.local 🎉

🔧 문제 생겼을 때 — 디버깅 명령어

증상 명령어
Pod가 Pending에서 안 넘어감
(노드 자원 부족 / PVC 못 받음 등)		 kubectl describe pod <name>
맨 아래 Events 보면 원인 나옴
Pod가 CrashLoopBackOff
(시작 → 죽음 → 재시작 → 또 죽음 반복)		 kubectl logs <pod-name>
앱 로그 확인
이전 Pod 로그 보고 싶음 kubectl logs <pod-name> --previous
Pod 안으로 직접 들어가기 kubectl exec -it <pod-name> -- sh
Backend가 MySQL에 못 붙음 Pod 안에서 nc -zv mysql 3306
다 지우고 다시 kubectl delete -f k8s/ 후 kubectl apply -f k8s/

☁️ Phase 7 — 진짜 클라우드에 배포

로컬에서 잘 돌면 다음 단계:

  1. 이미지를 인터넷 저장소에 올리기
    • Docker Hub — 가장 흔한 무료 저장소, public 이미지 무료
    • GHCR — GitHub Container Registry, private도 무료 한도 큼
    • AWS ECR — AWS 인프라용
  2. 실제 K8s 클러스터 받기
    • EKS / GKE / AKS — AWS/GCP/Azure의 매니지드 K8s (월 수만 원~)
    • DigitalOcean Kubernetes — 월 $12부터, 학습용 추천
    • k3s — 가벼운 K8s, 단일 VPS에 셀프 호스팅
  3. kubectl config로 클러스터 가리킨 후 kubectl apply -f k8s/
  4. 도메인 + TLS 인증서 — cert-manager(TLS 인증서 자동 발급/갱신 도구)로 Let's Encrypt(무료 HTTPS 인증서 발급 기관) 자동 발급
💸 비용 주의: 매니지드 K8s는 비쌉니다. 학습용이면 EKS보다 DigitalOcean Kubernetes ($12/월~) 또는 k3s를 단일 VPS에 띄우는 게 저렴해요.

🎯 한 줄 요약

Dockerfile 2개 + YAML 7개를 만들고 kubectl apply -f k8s/ 한 번이면 클러스터에 떠요.

진짜 어려운 건 K8s 자체보다 ① 각 컴포넌트가 환경변수로 잘 분리돼 있나, ② Secret을 안전하게 다루는가입니다.
