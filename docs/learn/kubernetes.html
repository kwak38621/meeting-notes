☸️ 쿠버네티스(Kubernetes) 쉽게 풀어보기 — 도대체 이게 뭐고 왜 쓰는가

전문 용어는 일단 쉬운 말로 풀고, 괄호에 진짜 이름을 같이 적어둘게요. 끝까지 보면 K8s가 뭔지 감이 잡힐 거예요.

📌 한 줄로 말하면

쉽게: 쿠버네티스는 "앱이 들어있는 상자(컨테이너) 수십·수백 개를 여러 서버에 자동으로 깔아주고, 죽으면 알아서 살려주고, 트래픽 많아지면 알아서 늘려주는 똑똑한 관리 시스템"이에요.
(진짜 이름: Kubernetes, 줄여서 K8s — k와 s 사이에 글자가 8개라서)

비교하면:

  • Docker = 앱을 상자에 포장하는 기계 (컨테이너 만들기)
  • 쿠버네티스 = 그 상자 수백 개를 굴리는 물류센터 관리자

🤔 왜 만들었나 — Docker만으론 뭐가 부족한가

Docker로 앱 하나 띄우는 건 쉽죠.

docker run -d -p 8080:8080 my-app:1.0

근데 진짜 서비스를 운영하면 이런 일이 생겨요:

  • "서버 한 대로 부족해서 3대에 똑같이 깔아야 함" → 일일이 ssh 들어가서?
  • "내가 잘 때 컨테이너가 죽었어" → 누가 살려?
  • "새 버전 배포할 건데 사용자한테 안 끊기게 하고 싶어" → 어떻게?
  • "방송 떠서 트래픽이 10배 됐어" → 자동으로 컨테이너 늘려주려면?
  • "컨테이너끼리 서로 통신해야 하는데 IP가 계속 바뀜" → 어떻게 찾아?
  • "DB 비밀번호를 컨테이너에 안전하게 넣고 싶어" → 어디에?

이걸 다 자동으로 해주는 게 쿠버네티스예요.

이런 문제가 생기면 쿠버네티스가 이렇게 해결
컨테이너가 갑자기 죽음 알아서 다시 살림 (self-healing)
여러 서버에 골고루 깔고 싶음 빈 서버 찾아서 알아서 배치 (scheduling)
새 버전 배포 하나씩 갈아끼워서 안 끊김 (rolling update)
트래픽 증가 알아서 컨테이너 복제본 늘림 (auto-scaling)
컨테이너끼리 서로 찾기 이름표로 찾을 수 있게 해줌 (service discovery)
비밀번호 안전 보관 금고에 따로 저장 (Secret)
"이전 버전으로 돌려" 명령 한 줄로 롤백 (rollout undo)

🏗️ 전체 그림 — 서버 묶음 한 덩어리 안에 뭐가 들었나

쉽게: 쿠버네티스로 묶인 서버들의 그룹을 "서버 묶음 한 덩어리"라고 보면 돼요. (Cluster, 클러스터)
그 안에는 두 종류의 서버가 있어요:
  • 지휘 본부 서버 — 명령 받고 결정만 함, 실제 앱은 안 돌아감 (Control Plane / Master Node)
  • 일꾼 서버 — 실제 앱 컨테이너가 돌아가는 곳 (Worker Node)
━━ 서버 묶음 한 덩어리 (Cluster) ━━

👀 Controller Manager 감시자 — "원한 상태 맞아?"

그리고 우리가 노트북에서 본부에 명령 보낼 때 쓰는 도구가:

→ 터미널에서 kubectl get pods 이렇게 치면 됨
💡 핵심 사고방식: 쿠버네티스는 "이렇게 됐으면 좋겠어"라고 말해두면 알아서 그 상태로 맞춰주는 시스템이에요. (이걸 "선언적(Declarative)"이라고 함)

예: "내 앱 상자 3개가 항상 떠 있었으면 좋겠어" → 1개가 죽으면 알아서 새로 띄움. "이제 5개로 바꿔" → 알아서 2개 더 띄움.

🧩 핵심 부품 7가지 — 하나씩 차근차근

1) 앱 상자 한 칸 (Pod)

쉽게: Docker 컨테이너를 한 겹 더 감싼 "상자"예요. 쿠버네티스는 컨테이너를 직접 안 다루고, 항상 이 상자 단위로 다룹니다. 보통 상자 1개 = 컨테이너 1개라고 보면 돼요. 
# pod.yaml (이런 식으로 적어요)
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
    - name: app
      image: my-app:1.0     # 어떤 이미지 쓸지
      ports:
        - containerPort: 8080

왜 한 겹 더 씌웠나? 가끔 한 상자 안에 컨테이너 여러 개를 넣고 같이 굴려야 할 때가 있어요 (예: 메인 앱 + 로그 수집기). 같은 상자 안에 있으면 같은 네트워크/저장소를 공유합니다.

2) 상자 관리 매니저 (Deployment)

쉽게: "이 상자를 항상 3개 유지해줘" 같은 약속을 받아두는 매니저예요. 상자가 죽으면 알아서 새로 만들고, 새 버전으로 바꾸면 하나씩 갈아끼워줍니다. 
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                    # ← 항상 3개 유지해줘
  selector:
    matchLabels:
      app: my-app                # ← 이 이름표 붙은 상자 관리
  template:                      # ← 어떤 상자를 만들지의 설계도
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: app
          image: my-app:1.0

이 파일 하나만 쿠버네티스에 던지면 상자 3개를 알아서 띄우고, 죽으면 살리고, 이미지를 1.1로 바꾸면 무중단 배포까지 해줍니다.

3) 대표 전화번호 (Service)

쉽게: 상자들은 IP가 매번 바뀝니다 (죽었다 살아나면 새 IP). 그래서 다른 상자가 "야, my-app 어딨어?" 할 때 IP로 찾으면 안 돼요.
"대표 전화번호"를 하나 부여해두고, 그 번호로 전화하면 살아있는 상자 중 하나에 알아서 연결시켜주는 게 Service. 
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app           # ← 다른 곳에서 "my-app:8080" 으로 부르면 됨
spec:
  selector:
    app: my-app          # ← 이 이름표 붙은 상자들로 트래픽 분배
  ports:
    - port: 8080
      targetPort: 8080
  type: ClusterIP        # 내부 전용

Service 종류 3가지 (전화번호의 범위):

  • 내선 전화 — 클러스터 안에서만 통함 (ClusterIP, 기본값)
  • 외부 공개 포트 — 서버의 특정 포트를 외부에 열어줌 (NodePort)
  • 클라우드 LB 연결 — AWS 로드밸런서 같은 거에 연결 (LoadBalancer)

4) 도메인별 안내 데스크 (Ingress)

쉽게: "api.example.com으로 들어오면 backend로 보내, www.example.com이면 frontend로 보내" 같은 안내 데스크예요. 도메인이나 URL 경로 보고 어디로 보낼지 결정. 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: backend-service     # ← 백엔드 대표번호로 전달
                port: { number: 8080 }
    - host: www.example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: frontend-service    # ← 프론트엔드 대표번호로 전달
                port: { number: 80 }

5) 설정값 보관함 (ConfigMap)

쉽게: "DB 주소", "CORS 허용 도메인" 같은 환경 설정값을 코드 밖에 따로 보관하는 곳. 환경(dev/운영)마다 다른 값을 넣을 수 있어요. 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "mysql.default.svc.cluster.local"
  CORS_ORIGIN: "https://app.example.com"

6) 비밀 금고 (Secret)

쉽게: 비밀번호, JWT 시크릿 같은 민감한 값 전용 보관함. ConfigMap이랑 거의 똑같은데 좀 더 엄격하게 다뤄지고, 값이 base64로 인코딩돼요.
⚠️ 주의: base64는 인코딩일 뿐 암호화가 아님. Secret yaml을 git에 그대로 올리면 누구나 디코딩 가능. 보관 방법은 적용 가이드 포스트에서 자세히 다룰게요.

7) 외장하드 (Volume / PersistentVolume)

쉽게: 상자(컨테이너)는 죽으면 그 안의 데이터도 사라져요. 그럼 MySQL 같은 DB는 어떻게 데이터를 안 잃지?
→ 상자 바깥에 외장하드를 따로 두고, 거기다 데이터 저장하는 방식.
신청서(PVC, PersistentVolumeClaim)로 "외장하드 10GB 주세요" 요청 → 실제 디스크(PV, PersistentVolume) 할당

       ▼

       ▼

       ▼

⌨️ 주문서(명령어) 모음 — kubectl

# 클러스터 상태 보기
kubectl get nodes                    # 서버 목록
kubectl get pods                     # 상자 목록
kubectl get deployments              # 매니저 목록
kubectl get services                 # 대표번호 목록
kubectl get all                      # 다 보기

# 설계도 적용/삭제
kubectl apply -f deployment.yaml     # 이 설계대로 만들어줘 (생성/업데이트)
kubectl delete -f deployment.yaml    # 지워

# 로그 / 디버깅
kubectl logs my-app-abc123           # 이 상자 로그
kubectl logs -f my-app-abc123        # 실시간 (tail -f)
kubectl exec -it my-app-abc123 -- bash   # 이 상자 안으로 들어가기
kubectl describe pod my-app-abc123   # 자세히 알려줘 (왜 안 떠?)

# 개수 조정
kubectl scale deployment my-app --replicas=5    # 5개로 바꿔줘

# 배포/롤백
kubectl rollout status deployment/my-app
kubectl rollout undo deployment/my-app          # 직전 버전으로 돌려

⚖️ 너한테 정말 필요한가?

이런 상황이면 써볼 만함 이런 상황이면 굳이 안 써도 됨
- 마이크로서비스가 여러 개
- 트래픽 변동이 큼
- 여러 환경(dev/stg/prod) 운영
- 팀에 DevOps 인력 있음
- 학습/이력서 목적 		- 1인 사이드 프로젝트
- 사용자 적음 (~수백 명)
- 앱 하나만 굴림
- 운영 인력 0명
- docker-compose로 충분히 돌아감
⚠️ 솔직한 조언: 쿠버네티스는 강력하지만 배우는 데 시간 진짜 많이 듭니다. 개인 프로젝트엔 실용적으론 과해요. 하지만 학습/포트폴리오 목적이면 정말 좋은 선택입니다. 회사 인프라가 어떻게 돌아가는지 이해하는 데 큰 도움 돼요.
